1 · 平台解决什么问题1 · What problem it solves

让"人 + 多个 AI agent"一起开发软件时，协作有秩序、质量有闸门、过程留得痕。具体治三种痛：

When humans and multiple AI agents build software together, signet keeps collaboration orderly, quality gated, and every step auditable. It cures three pains:

① 需求被做歪① Requirements drift
口头/聊天交代的需求，agent 按自己的理解就开工，交付时才发现理解错了，返工成本巨大。
Work starts from chat messages; the agent interprets freely; the mismatch surfaces only at delivery — when rework is most expensive.
对策：先冻结判据，再动手。 Fix: criteria are frozen before any work starts.
② 验收走过场② Rubber-stamp review
agent 说"做完了"，人看不懂代码只能点头。机器断言没人写，人工检查没清单。
The agent says "done"; the human can't read the code and just nods. No machine checks, no review checklist.
对策：每条验收标准配机器用例 + 人工走查项。 Fix: every acceptance criterion gets machine cases plus human walkthrough items.
③ 过程没记忆③ No institutional memory
session 一关，决策依据、踩坑教训全丢。新 session 从零开始，重复犯错。
Close a session and the reasoning, decisions and lessons vanish. New sessions start from zero and repeat mistakes.
对策：账本唯一事实源，设计裁定与经验全部入库。 Fix: the ledger is the single source of truth; rulings and lessons are written into it.
一句话定位：signet 把"需求 → 任务 → 冻结 → 派活 → 实现 → 验收 → 入库"变成一条有状态机、有凭证、有审计的流水线。一切材料经 API 获取，一切状态变更经动词落账，一切裁定可追溯。 In one sentence: signet turns "requirement → task → freeze → dispatch → implement → verify → ship" into a pipeline with a state machine, credentials and an audit trail. All materials are fetched via API; every state change goes through a verb; every ruling is traceable.

三条回环：驳回（Implemented→Ready，整改后凭原 sigt 重领）；重冻（合同变更把已实现打回就绪，内建 reject 效果）；返场（同一 sigt 幂等重 claim，租约续期）。状态只许前进或由这三个动词回退——没有"悄悄改状态"的通道。 Three loops: reject (Implemented→Ready, re-claim with the same sigt after fixes); refreeze (a contract change bounces Implemented back to Ready — a built-in reject); rebound (idempotent re-claim with the same sigt, lease renewed). States only move forward or back via these three verbs — there is no "quietly edit the state" path.

4 · 凭证与权限体系4 · Credentials & permissions

4.1 三类凭证，各管一件事4.1 Three credential types, one job each

你（人）You (human)权威的唯一来源the sole source of authority
登录态Login session页面 cookie / CLI 令牌——证明"这是你本人"Cookie / CLI token — proves "it's really you"
PAT个人 API 令牌——agent 替你写需求用（按 scope 授权动词）Personal token — lets an agent draft requirements for you (verb scopes)
SIGT任务委托令牌——你授权某 agent 做某任务（一牌一任务）Task delegation token — you authorize an agent for one task (one token, one task)
记住一个类比：PAT 像"你签名的空白委托书（限定了能办的事）"，SIGT 像"派工单（限定到具体任务）"。两者都只授权、不转移问责——出了事账本上记的是签发人（你），执行者记在 on_behalf_of 备查。agent 没有、也不需要独立账号。 An analogy: a PAT is like "a pre-signed letter of attorney (limited to listed affairs)"; a SIGT is like "a work order (bound to one specific task)". Both authorize without transferring accountability — the ledger records the issuer (you) as the accountable actor, with the executor in on_behalf_of for reference. Agents have no accounts of their own, and need none.

7 · 常见问题7 · FAQ

Q1：和"直接在聊天里让 agent 写代码"有什么区别？Q1: How is this different from just asking an agent to code in chat?
聊天开发把需求、实现、验收揉在一次对话里，质量靠运气、过程没记忆。signet 把三者拆开：需求先逐条确认成判据，实现照冻结合同自验，验收有机器用例兜底——交付物可以复验，过程全在账上，换 session 不丢上下文。
Chat-based coding mixes requirements, implementation and review in one conversation — quality is luck and nothing is remembered. signet separates the three: requirements are confirmed entry by entry into criteria, implementation self-verifies against a frozen contract, and machine cases back the review. Deliverables are re-verifiable and the process is on the ledger; switching sessions loses nothing.
Q2：agent 的 session 做到一半关了怎么办？Q2: What if an agent's session dies mid-task?
不用抢救 session。任务、租约、上下文都在账上：开一个新 session，用原 sigt 重新 claim（幂等接管，租约续期），读工作区里的任务包和 handoff 文件接着干。平台的整个设计就是为了让 session 可以随时死、随时换。
No need to rescue the session. Task, lease and context live on the ledger: open a new session, re-claim with the same sigt (idempotent, lease renewed), read the workspace package and handoff notes, continue. The platform is designed so sessions can die and be replaced at any moment.
Q3：任务被驳回（reject）了怎么办？Q3: What if a task is rejected?
驳回是回环不是终点：任务回 Ready，驳回理由落账。实现 session 整改后用原 sigt重领，重跑用例再交。若反复驳回仍不过，operator 会把它提给您裁决（阻塞/换实现方/降级范围）。
Rejection is a loop, not an end: the task returns to Ready with the reason recorded. The implementing session fixes it, re-claims with the same sigt, re-runs cases and resubmits. Repeated failures escalate to you (block / swap implementer / shrink scope).
Q4：需求确认（confirmed）之后还能改吗？Q4: Can a confirmed requirement still change?
confirmed 是需求的"冻结"——API 不再接受修订。判据确实有错时的正规出路：登记新需求或新条目走一遍确认流（旧条目留档）；纯格式修正由 operator 直改+commit 披露（现有簿记 SOP）。改已确认条目而不留痕，等于绕过整个体系。
Confirmed is the requirement's "freeze" — the API no longer accepts edits. If an entry is genuinely wrong: register a new requirement or entry and run it through confirmation (old kept). Pure formatting fixes go through the operator direct-edit-with-disclosure SOP. Silently editing confirmed entries bypasses the whole system.
Q5：数据存在哪？需要数据库吗？Q5: Where does data live? Is a database needed?
不需要。git 状态仓是唯一事实源：账本事件流、任务、需求、冻结规格、设计稿、经验全在里面，可克隆、可 diff、可审计。数据库将来只用于派生数据（指标缓存），真相永远在 git。
No. The git state repository is the single source of truth: event stream, tasks, requirements, frozen specs, design docs and lessons all live there — clonable, diffable, auditable. Databases, if ever introduced, hold only derived data (metrics caches); truth stays in git.
Q6：现在能开多个项目吗？Q6: Can I run multiple projects now?
当前一个服务实例绑定一个项目（状态仓）。多 project 支持（页面注册 + 服务端克隆 + 样板骨架）已列入路线：api-remote-ready 落地后即立项，这是"换一个真实项目"的前置。
Today one service instance binds one project (one state repo). Multi-project support (UI registration + server-side clone + starter skeleton) is on the roadmap: it gets scheduled right after api-remote-ready ships — the prerequisite for onboarding a real second project.
Q7：平台看着没反应 / 报错了，第一步查什么？Q7: The platform seems unresponsive — what do I check first?
① 服务探针 curl 127.0.0.1:8000/api/health；② 服务日志 workspaces/signet-8000.log；③ 服务是孤儿进程形态，重启命令和部署坐标都在 hints.md「本机部署坐标」；④ 重启不会动账本，但全量 token 会失效——CLI 重新 login 即可。
① health probe curl 127.0.0.1:8000/api/health; ② service log workspaces/signet-8000.log; ③ the service runs as an orphan process — restart command and coordinates are in hints.md "Local deployment"; ④ restarting never touches the ledger, but invalidates all tokens — just log in again via CLI.
