目标

页面的人视图层全部改说人话：事件流可读、任务可辨认（短码+标题）、时间可感知（相对时间），且不动账本与 API 的事件结构。

需求 → 任务派生流（v0.8.6 模型，本页即此流的视图）
  • 判据条目 = 派生锚点：一条条目派生一个 task（返场/另切再派）；条目与 task 是 1:N。
  • 派生动作 = init-task（预填 requirement + 条目号）→ Draft（起草 agent 生成三件套）→ 签署 freeze → Ready → 领取执行 → Done ⇒ 条目覆盖。
  • 需求进度 = 条目 Done 数 / 总条目数（非任务数口径）。
  • 数据落点：task.md 记 requirement + req_item；需求页据此反查"哪个条目由哪条任务承载"。条目级关联平台待实现（backlog EN-04），本页为设计基准。
  • 三道闸门（requirement-management REQ-6）：G1 需求逐条确认（未确认不可派生）→ G2 三件套每条 AC 可追溯到已确认条目 + 机检绿（含 fixture 冒烟）→ G3 H1/H2 双签 freeze。闸门防两类事故：任务跑偏、合同缺陷。
  • confirm ≠ 派生：confirm 是质量闸门（"立不立得住"，整篇一次）；派生是调度决策（"现在做不做、从哪条做起"，按条目可分批）。确认不派生的正常场景：排队等排期 / 分批推进（先 REQ-1 后 REQ-5）/ 等前置需求 / 纯目标登记（confirm 后归档）。confirm 完成态直接给「立即派生」入口，动线相邻。
条目的三个职责（人不是只点「派生」）
  • 验收基准的锚：task 三件套里每条 AC 都应挂到某个条目——条目是"为什么有这条验收"的出处，需求进度按条目覆盖率算。
  • 判据质量闸门：条目由人逐条确认/修订（草案由起草 agent 生成，确认 ≠ 起草者）；条目质量决定派生 task 的质量。
  • 收口确认：需求完成 = 条目全 Done + 人确认动作（落事件）。
条目无独立状态机：状态由「需求确认 + 承载任务」推导——草案（需求 draft） → 已确认（需求 confirmed） → 已派生（有承载 task）→ 已覆盖（承载 task Done）；条目确认并入需求 confirm（逐条打勾是 UX，落一个事件）。
