新建需求

主路径：起草流（人配合 agent 产生需求）

一句话动机 → 你在用户 settings 生成起草令牌 PAT（绑你 + scope=需求起草 + 执行者标签 + 过期）交给 session 里的起草 agent——agent 无自有账号，令牌本质是你对这个 session 的授权 → agent 与你对话澄清 → 生成 requirement.md + 判据条目草案 → submit 请你确认 → 你本人登录逐条打勾 confirm → 生效可派生。

去 settings 生成 PAT + 派活卡

动作集仅 5 个动词（create / update / submit / confirm / archive），复用提案+sync 与事件链；归因双字段随凭证：actor=你（问责）、on_behalf_of=执行者标签（归属）。

需求从哪来（三个口，都是先成需求再派任务）
  • 使用反馈：页面走查 / 使用中发现的问题（如 page-human-readable 来自"事件流看不懂"）。
  • backlog 归并：改进点候车道分拣时「立为新需求」（如本需求来自走查缺口）。
  • 讨论沉淀：开发过程中的痛与想法（如 task-collab-mailbox 来自 T6 人肉传话）。
需求不是凭空写的文档：先有一句话的真实动机，再起草成「目标 + 判据条目」结构。

辅路径：表单直录（你已经有成稿内容）

模式 B：起草流（只有一句话想法，让 agent 起草）

填一句话动机 → 平台生成「需求起草任务」（Draft）→ 你接取开 session → 起草 agent 生成 requirement.md + 判据条目草案 → 你逐条确认 / 修订 → 入账 accepted。

起草流复用 Draft 任务机制（接取/起草/提交/确认），与三件套起草同一套"起草 ≠ 确认"闸门。
